# [T129] Amend the durable contracts for what v3.0 actually shipped

milestone: v3.0 · track: docs · depends_on: T127 · provides: `ARCHITECTURE.md`, `PROJECT_STRUCTURE.md` and `ROADMAP.md` describe the multi-project console that now exists — the three registry endpoints, the changed `/health` and `/events`, per-request resolution, and the v3.0/v3.0.1 split.

## Context

**This ticket exists because v2.2's T94 exists.** That ticket was filed because user and contributor
docs still stated the pre-T78 run-state contract months after the code had moved on, and the root
cause was that the milestone which changed the contract did not amend the document that states it.
v3.0 changes the durable REST contract in four ways, and without this ticket the same gap reopens:

- Three new endpoints (`GET /api/v1/projects`, `GET /api/v1/projects/current`, and the three
  mutations) are absent from the "REST v1" list.
- `GET /api/v1/health` narrows from `{ ok, version, projectRoot }` to a **nullable** `projectRoot`
  plus a new `selectionReason` — the current line in ARCHITECTURE.md becomes wrong.
- `/events` gains a terminal `event: stale` frame and a per-connection project binding.
- The document still describes "one `Project` fixed at boot" as the architecture and the whole v3
  section as PLANNED, when per-request resolution has shipped.

`ROADMAP.md` also needs the v3.0/v3.0.1 split reconciled against its v3 epic bullets.

It lands at the END of the milestone, after T127 proves the behaviour, so it documents what was built
rather than what was intended.

## Staged approach

1. `docs/planning/ARCHITECTURE.md`:
   - **REST v1** — add `GET /api/v1/projects`, `GET /api/v1/projects/current`,
     `POST /api/v1/projects`, `DELETE /api/v1/projects/{id}`, `PUT /api/v1/projects/current` with
     their shapes and their write-token gating; correct the `/health` line to the nullable
     `projectRoot` + `selectionReason`; add the `/events` per-connection binding and the `stale`
     frame to that entry.
   - **Contracts** — a short "ProjectRegistry port" subsection (by reference to
     `store/registry_protocol.py`, not re-specified) and the `ProjectConditionProbe` beside it; state
     the canonical-path rule and that the DATABASE's UNIQUE index is the duplicate authority.
   - **Data model** — the `RegisteredProject` / `RegistryEntry` rows T103 added get their REST-facing
     counterpart named, and the selection-failure union is stated once as the shared vocabulary.
   - **Cross-cutting** — record that the selection is persisted in `console_state`, that the pinned
     PATH is the session's initial selection (T111's precedence rule), and that the console db is the
     only writable state outside a target project.
   - **The v3 section** — rewrite from planned to **shipped for v3.0**, keeping the v3.1+ bullets as
     forward-looking. Note explicitly what v3.0 did NOT do: no `serve`, no auth, no bind change, no
     CLI subcommand.
   - Update the "Concurrency" note's list of still-inline handlers — T116–T118 converted nine of
     them.
2. `docs/planning/PROJECT_STRUCTURE.md`: add `frontend/src/routes/projects/`, `store/entries.py`,
   `services/project_selection.py`, `services/watcher_supervisor.py`,
   `file_adapter/project_condition.py` and `api/v1/projects.py` to the tree. (T103 already added the
   `store` and `github` ownership rows and the `domain/`-is-shared rule.)
3. `docs/planning/ROADMAP.md`: replace the v3 epic's v3.0 bullet with the shipped checklist and add
   the v3.0.1 section, keeping v3.1+ as epics. Note the split and why it was made.
4. **Re-read every changed paragraph against the shipped behaviour before committing** — the T94
   failure mode is docs that were true when written.
